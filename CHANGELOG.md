# Changelog

## Unreleased

- Source Control now follows the selected herdr space and keeps only that space's repository: the longest open root that equals or contains the followed folder. A followed linked worktree keeps its own repository and its main checkout is dropped. A space with Git shows that repository's changes; a space without Git shows the Initialize offer. This fixes a repository nested in a followed non-repository folder (`C:\Users\me\Projects\parentdir\nestedrepo`, opened by Git's startup scan while `parentdir` was followed) showing, and staying open after the switch away.
- The navigator workspace file now carries `git.autoRepositoryDetection: false`, `git.detectSubmodules: false`, `git.detectWorktrees: false`, `git.openRepositoryInParentFolders: "always"` and `scm.repositories.selectionMode: "single"`. The `git` keys stop sub-folder, submodule and worktree detection, and open the parent repository for a folder inside one. The `scm` key keeps a newly opened repository out of the Changes view until the old one goes. New files get them at creation; an open navigator window gets them at activation through the configuration API, no reload needed, and a different value of these five in that file is overwritten. They override your user settings in that window only.
- The extension's empty anchor folder now holds `.vscode/settings.json` with `git.enabled: false`, so Git never opens it as a repository.
- Any other repository that still opens in a navigator window (nested in the followed folder, kept by a visible editor after a switch, re-detected through a followed repository's own `.vscode/settings.json`, or opened by hand) is dropped at activation, after a folder change and on each repository open, every time. The drop first lists the root in workspace `git.ignoredRepositories`, which keeps Git from reopening it, then briefly sets workspace `git.enabled` to false and removes it. That leaves no "previously closed" entry, so the Initialize offer still shows, and `git.close` is never used. A visible editor of a dropped repository keeps its tab.
- The workspace `git.ignoredRepositories` list starts from your user-level list and stays in the navigator file. Following a space leaves out any entry that would stop its repository, even one from your user-level list, so that repository opens again. `Git: Open Repository` on a listed nested repository or worktree opens nothing and shows no message.
- A switch in a navigator window replaces every folder after the anchor with the target in one update, so the window holds the anchor and the followed folder. A folder you add by hand goes at the next switch.
- A switch to a space with Git now opens the target's repository first and swaps the folder after, so Source Control goes straight from the old repository to the new one, with no empty view and no second section in the Changes view. Over 20 switches the old repository closed a median of 26 ms after the new one opened, 76 ms at most, with no `scm: dropping` line. Explorer and the window title change later, by the time the repository takes to open. The wait stops at 2000 ms: the switch then goes on and the log has `scm: <root> is still opening past the bound, the switch goes on`. A failed open still swaps, and a target with no Git swaps with no wait.
- A `git init` in the followed space's terminal now shows the repository with no switch, 1316 to 1407 ms later as measured. Git's own `.git` watcher is off under `git.autoRepositoryDetection: false`, so the extension watches the followed folder for `.git` and `.git/HEAD`.
- The extension's own Initialize button and its command `herdrNavigator.initRepository` are removed. A space without Git shows Git's own Initialize Repository button and VS Code's built-in "Publish to GitHub" block.
- Either pick of Git's Initialize button attaches the followed folder's repository with no reload. The pick lists the anchor first and selected, so Enter takes it: the extension removes the fresh `.git` that creates and initializes the followed folder through Git. Running the button's command, the repository showed 1289 ms after the anchor pick and 177 ms after the followed folder's pick. A `.git` is fresh when it holds `HEAD` with no `refs/heads` entry, no `packed-refs` and no `index`; any other stays, and the log says so. The same check at activation removes a fresh `.git` an earlier build left in the anchor, and initializes nothing.
- `followMode: folder` is a plain folder window, so none of this applies there. With `herdrNavigator.followGitRoot` off, the exact folder is followed and its parent repository shows.
- Known limits:
  - A switch away from a repository with a file in a visible editor keeps that repository open past the swap, so it still goes through the `git.enabled` toggle and the list empties for a moment: 116 ms in the one run measured. Initialize text showing in that gap is inferred; that switch was not filmed.
  - With the Repositories pane enabled, hidden by default, both repositories show there while the old one closes.
  - Git redraws the view during a switch. Films of 20 switches at one frame per 266 ms showed up to about four changed frames per switch, some with a bare input box, always one section and no Initialize text. The overlap itself is shorter than that frame period; a 300 ms hold between open and swap, filmed separately, is what shows one section across it.
  - A space change in the 1 second wait after Git's Initialize pick removes a fresh anchor `.git` and initializes nothing, and the log has `scm: not initialising <folder>, the space changed after the pick`.
  - The first start after upgrading an existing navigator file runs Git's startup scan before the settings are written, so a nested repository can appear until the activation pass drops it.
  - A drop turns Git off for 33-47 ms as measured; whether a flash shows is unmeasured. It runs only when a stray repository exists.
  - Commit text set through the Git API, with the Source Control view open, stayed in the input box of the reopened followed repository in the one run measured. Hand-typed text and a closed view are unmeasured.
  - A drop does not kill a running Git command, so the Source Control spinner stays until the command ends, while the reopened repository works.
  - The one exception VS Code leaves: any repository under a folder whose own `.vscode/settings.json` sets `git.enabled: true`. A folder value outranks the workspace value, so the toggle never disposes it. The extension tries one drop and logs `scm: left open <root>: it outlived the git.enabled false, so its own folder's settings keep Git on there` once. For a folder added by hand (0 close events measured across it), the next switch removes the folder and its repository. For a stray inside the followed folder (read from Git's source and the guard's code, not measured live), the next switch to another folder takes the followed folder out of the window and drops the stray.
  - A real reopen loop: after four drops of one root within 10 seconds, the extension leaves it open and logs `scm: left open <root>: Git keeps reopening it right after each drop`. A later event past those 10 seconds drops it again, and a folder change clears the count. No live scenario reached this limit.
  - While the navigator workspace file has unsaved changes, VS Code rejects the extension's writes, so a stray stays until the file is saved and the log has `scm: reconcile stopped, a later event retries it`. It went about 260 ms after the save as measured.
  - If turning Git back on fails after 3 retries, Git stays off in that window until a later event retries it, and the log says so.
  - A followed folder or repository root whose real path does not resolve is compared as written, and the log has `scm: no real path for <path>, comparing it as written`. It keeps nothing open, so a repository behind a junction or mapped drive that does not resolve counts as a stray and is dropped.
  - With `files.watcherExclude` covering `.git/HEAD`, a `git init` slower than the extension's 1 second wait shows at the next event instead.
  - An adopted legacy anchor whose settings file already exists without `git.enabled` lets Git open a `.git` there, until the extension drops it.

## v0.2.2 — 2026-11-03

- When the followed folder is a linked git worktree, the workspace folder in the Explorer and the status bar label now show the main project's name instead of the worktree's folder name. The name is read from the worktree's `.git` file, so it works whether the main project is a normal checkout, a bare repository (`<project>.git`) or a `.bare` layout. Folders that are not a worktree root (plain repositories, submodules, subfolders) keep their own name.
- A workspace folder already open under the worktree's folder name is renamed in place, including after a window reload.

## v0.2.1 — 2026-11-03

- Fixed a unit test that assumed Windows path separators, so the release build's test step passes on Linux. v0.2.0 was tagged but never published; v0.2.1 is the first 0.2 release.

## v0.2.0 — 2026-11-03

- Removed the session folder repair added in v0.1.3: the command `Herdr Navigator: Repair herdr session folders` (`herdrNavigator.repairSessionFolders`), the setting `herdrNavigator.repairSessionOnLaunch` and the restore manifest written to the extension's global storage are gone. herdr's own session restore is used as is.
- The extension no longer writes, renames or backs up herdr's `session.json`, and never changes herdr's saved state.
- Existing `herdr-session-backups/` folders and `restore-manifest.json` files left in the extension's global storage by v0.1.3 are not deleted; you may remove them by hand.
- Removed the `scripts/jump-list-repro` dev script, because it could not be isolated from the default herdr session.
- Clicking the status bar item to attach to an already-running herdr server no longer re-focuses the last remembered space, so it no longer moves the focus of other herdr clients. Restoring a window still re-focuses the remembered space.
- The optional herdr plugin id is now `zenderx.herdr-navigator` (renamed from `zenderx.refocus-last-space`). The extension detects the new id; unlink the old plugin and install the plugin again.
- New "Open in VS Code" action in the optional herdr plugin. It opens a `vscode://z3nder.herdr-navigator/open?space=<id>[&session=<name>]` link; the extension validates it, shows the matching herdr terminal (or opens one in the editor area) and focuses the requested space. Bind it in herdr's `config.toml`; see docs/open-in-vscode.md.
- The optional herdr plugin now returns restored panes to their last live folder (herdr issue #5199) by typing `cd '<folder>'` into idle shells it just restored. See plugin/README.md.
- Without the plugin, the extension now returns restored panes to their last live folder itself (herdr issue #5199), with no shell configuration. While the navigator window is connected to herdr (whether or not it hosts it) it records each pane's live folder, the folder it was spawned in and its shell process id, in `cwd-return-<key>.json` in its global storage, without polling: from herdr's pushed `pane_updated`, `pane_created` and `pane_moved` events, dropping panes on `pane_closed`, `pane_exited` and `pane_moved`, and from a full snapshot when it connects, on each space, tab or pane focus change, when a tab or space closes and after a return. For Git Bash on Windows, whose herdr `cwd` stays at the spawn folder, it reads the live folder from the MSYS shell process (`/proc/<pid>/cwd`) on those same events, one Git Bash run for all panes. herdr fires no event on a `cd` or a stop, so a `cd` under a prompt that sets no title (starship, a custom `PS1`) followed by a stop with no event in between is recorded as of the last event; Git's stock prompt sets the title, so its `cd`s push `pane_updated`. A pane whose id herdr reused for a different spawn folder is skipped as `mismatch`. After it sees the herdr server restart (the connection was lost and came back, or, when the window starts, a recorded pane's shell process id changed) it sends `cd '<folder>'` plus Enter (socket request `pane.send_input`, the only new request it may send) into idle shells with no agent whose folder exists and differs from the record: a Git Bash pane as soon as its shell process exists (input typed ahead of the first prompt runs correctly, measured), any other shell once herdr reports its first prompt, waiting up to 20 s. It acts only from the window holding the navigator lease, writes one `cwd-return:` line to the output channel per run, and defers to the plugin when `herdr plugin list --json` reports it installed and enabled. It never writes `session.json` or creates, closes or renames anything. This is to be removed once herdr restores pane folders itself.
- Spawn-folder check for the extension's return: a pane is `cd`'d only when the spawn folder stored before the restart and the restored pane's spawn folder are both known and equal. The restored side is the pane's spawn-form reading or else the `pane.process_info` the busy check already fetches, so a reconnect seconds after the restart is checked too; the stored side is seeded from `pane.process_info` for every entry without one (including records written by 0.1.3) and refreshed when a pane's recorded folder changes, never from a restored pane before its own decision. New skip reason `unknown-spawn` (before `mismatch`) when either side is unknown; such a pane stays in herdr's folder. After upgrading, let VS Code connect once to the running herdr server before its next restart, so the old record gets its spawn folders.
- After upgrading, the first activation misses a restart that happened while VS Code was closed, because the old record holds no shell process ids; a restart seen as a lost and restored connection is unaffected.
- Return: a busy restored shell is no longer skipped at the first look. A fresh Git Bash login shell runs its profile's and prompt's child processes (starship, for one) for some seconds after a restart, which counted as busy, so its pane was skipped as `busy` and its spawn folder was then recorded over the folder to return to. A busy pane is now checked again every second, with a fresh process table, until it is idle and gets its `cd`, or the 20 s readiness window ends and it is logged as `busy-timeout`. A pane skipped as `busy-timeout` or `not-ready` keeps its recorded folder and shell process id until the next return run, so the next VS Code start or herdr server restart still sees the restart and returns it.
- PowerShell: herdr's own PowerShell integration reports the folder (OSC 9;9) and herdr restores PowerShell panes in their live folder itself, so the return normally leaves them as they are (`same`).
- Linux: the plugin's sh scripts were run live against herdr 0.9.5 in a Debian container (`scripts/cwd-restore-probe/linux/`); herdr restores the live folder on Linux, so the return is normally a no-op there. macOS is untested.
- Follow: on a `pane_updated` push for the focused pane, the extension now reads the shell's live folder through its probe, so a `cd` under Git's stock prompt is followed with no shell configuration. A prompt that sets no title fires no event on `cd`, so that `cd` is followed at the next focus, pane or tab change. The `herdrNavigator.cwdPollMs` timer is unchanged and never runs the probe. The `hint:` log line now names the `herdrNavigator.liveCwdProbe` and `herdrNavigator.gitBashPath` settings.
- Nothing needs to be added to `~/.bashrc`, `$PROFILE` or any other shell startup file, and no feature depends on a shell snippet. The shell integration doc and its OSC 7 snippet are gone; if you added an earlier snippet you may remove it, nothing uses it.
- When herdr is installed but the optional `zenderx.herdr-navigator` plugin is not installed or not enabled, a small plug icon appears immediately to the right of the herdr status bar item (the auto-follow toggle); both items have fixed priorities so no other extension's item lands between them. Clicking it explains the plugin and offers Install (runs `herdr plugin install ZenderX/herdr-vscode-navigator/plugin` in a visible terminal, where herdr asks for confirmation), Learn more, and Don't show again (remembered across reloads and synced). The plugin is checked at startup, when herdr first appears, and after the install terminal closes. New command `herdrNavigator.pluginHint`.
- When herdr is not installed the status bar item now reads `herdr: not installed` and a click opens herdr's install page (https://herdr.dev/docs/install/). The extension looks again for herdr when the window regains focus and on that click, so a fresh install is picked up without a reload. New command `herdrNavigator.openHerdrInstall` (Herdr: Open Herdr Install Page).
- Clicking the status bar item now launches herdr in an editor-area terminal tab when herdr is not running in this window, and toggles auto-follow when it is; the tooltip names the action. New command `herdrNavigator.launchHerdr` (Herdr: Launch Herdr).
- The status bar item now shows auto-follow state at a glance: an open eye when on, a dimmed closed eye when off.
- After launching herdr (status bar click or auto-launch on restore) the extension now defers re-focusing the last space to the optional `zenderx.herdr-navigator` herdr plugin when it is installed and enabled (one `herdr plugin list --json` call per launch), and falls back to its own re-focus otherwise.
- The workspace name in the navigator's title bar now shows the focused herdr space's label instead of `herdr-navigation (Workspace)`, and follows the focused space without a reload while auto-follow is on (a space rename shows at the next focus change). With the herdr terminal tab active the title reads `herdr - <space> - Visual Studio Code`; `herdr` there is the active editor, not part of the extension's value. Titles written by 0.1.x are migrated on first run; a `window.title` you set yourself in the workspace is left alone.
- Fixed a duplicate herdr tab after restoring a window: when VS Code revives the previous herdr terminal after auto-launch has already created its own, the extension now closes the empty revived tab, but only after a process-tree scan shows no herdr client in it (never one that was used, or whose state cannot be determined).
- Known limit: the Explorer header still reads `NAVIGATOR (WORKSPACE)`. VS Code derives it from the saved workspace file name plus a hardcoded suffix and offers no API to change it; renaming the file to follow the space would reload the window on every space switch.
- Releases are now built by a GitHub Actions workflow with a signed build provenance attestation. See [Verifying a release](https://github.com/ZenderX/herdr-vscode-navigator/blob/main/docs/verifying-releases.md).

## v0.1.3 — 2026-10-21

- Session folder repair: herdr 0.9.5 restores panes in the folder they were spawned in, not the one they were in when it stopped. While this window hosts herdr, the extension records each pane's live folder; when auto-launch finds the herdr server stopped, it fixes pane `cwd` and workspace `identity_cwd` in herdr's `session.json` before starting herdr. It saves a backup first (newest five kept, under the extension's global storage) and leaves the file alone if the schema version is not 3 or anything does not match. Named sessions (`HERDR_SESSION`) and `HERDR_CONFIG_PATH` are skipped. A pane that moved into another repository keeps its old worktree grouping.
- New command `herdrNavigator.repairSessionFolders` (Herdr Navigator: Repair herdr session folders), for after a manual stop of herdr and before relaunching it.
- New setting `herdrNavigator.repairSessionOnLaunch` (default `true`): run the repair before auto-launch starts herdr.
- `scripts/session-restore-probe/` holds the isolated probes, including `repair-e2e.mjs`.

## v0.1.1 — 2026-10-20

- Windows that do not host herdr scan their terminals' processes far less: herdr focus events trigger at most one scan per 30 s (was 5 s); a command starting in a terminal (shell integration) triggers one after about a second.
- The `cd` poll now asks herdr for the focused pane only (`pane.get`) instead of the full session snapshot each tick; it falls back to a snapshot when the focused pane is unknown, gone, or no longer focused.
- The navigator workspace is now a saved file, `navigator.code-workspace`, in the anchor folder under the extension's global storage, instead of an untitled workspace. VS Code always restores untitled workspaces at startup, so starting it with a folder (taskbar jump list, `code <folder>`) left a second restored navigator window; a saved workspace is restored only when VS Code starts without a folder.
- Opening a folder after a session in which the navigator ran, with no navigator window of the current VS Code launch alive, makes the window you opened the navigator: it converts to `[anchor, <folder>]` (one reload) and hosts herdr focused on that folder.
- Converting a single-folder window (first follow, or herdr started by hand) now reloads the window once; herdr's panes keep running and herdr is relaunched in the converted window.
- One-time migration: an existing untitled navigator workspace is moved to the saved file after a message from the extension; VS Code asks once to save the old untitled workspace (choose Don't Save).
- The navigator's session record is kept in `globalState` so a plain-folder window can read it; the takeover is skipped when `herdrNavigator.followMode` is `folder`.
- `scripts/jump-list-repro/` reproduces the jump-list launch in an isolated VS Code and herdr.

## v0.1.0 — 2026-10-19

- Initial release: follows the focused herdr pane's working directory, so the editor's file tree tracks herdr's focus.
- Follow modes (`herdrNavigator.followMode`): `workspace` (default) keeps an extension-owned empty anchor folder plus a replaceable second root with no reloads after the first conversion; `folder` opens the followed directory as the window's single folder, which reloads the window on every switch.
- Git-root following (`herdrNavigator.followGitRoot`, default on): the followed directory snaps to the root of its Git repository; outside a repository the exact directory is followed.
- `cd` following: the extension polls the focused pane's directory every `herdrNavigator.cwdPollMs` milliseconds (default `1000`, minimum 250, `0` disables) while this window hosts herdr and auto-follow is on.
- Live cwd probe (`herdrNavigator.liveCwdProbe`, default on): resolves the focused pane's live directory from its shell process on Linux, macOS and Windows (Git Bash via `herdrNavigator.gitBashPath`).
- Commands: follow now, toggle auto-follow, reconnect, show diagnostics; two-step chord keybinding; status bar item.
- Settings: `autoFollow`, `socketPath`, `cwdSource`, `followMode`, `followGitRoot`, `debounceMs`, `cwdPollMs`, `liveCwdProbe`, `gitBashPath`.
- Cross-platform: Windows named pipe, and a Unix socket on Linux and macOS.
- Window title: a navigator window shows `herdr-navigation (Workspace)` instead of `Untitled (Workspace)`, written to the workspace-scope `window.title` only.
- Auto-launch (`herdrNavigator.autoLaunch`, default on): when VS Code restores a navigator window in which herdr was running, herdr is relaunched in an editor-area terminal (reusing the revived `herdr` tab) and the previously selected space is focused again via `workspace.focus`.
- The docs recommended an optional OSC 7 snippet for Git Bash on Windows.
